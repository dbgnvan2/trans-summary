## Executive summary

This review surfaced 40 verified findings; the load-bearing risks cluster in the fail-closed publish core (release gate, faithfulness/theme judges, validators) and in shareable output safety. Fix five things first. (1) faithfulness_judge.py:136 unconditionally strips any leading "<=40-char prefix:" from a claim line before the armed Hard-BLOCK judge sees it, so a fabricated citation/attribution phrased as "Stanford study: ..." is deleted and rides through the gate — a genuine gate bypass the idealized gold set never exercises. (2) The DEFAULT "V2 (Safe)" initial validator (transcript_initial_validation_v2.py:233) catches exhausted-retry API errors and returns [], silently dropping a whole chunk's findings so a partially-validated transcript ships as clean — the exact fail-open pattern the v1 sibling deliberately raises on. (3) markdown_to_html (transcript_utils.py:1642) never escapes, and every template block renders with |safe, so raw transcript/LLM text yields stored XSS in the distributed HTML/PDF bundle. (4) A valid-JSON non-dict in logs/runtime_settings.json (config.py:64) raises AttributeError at module import, taking down the GUI and every pipeline stage with no self-recovery. (5) The fuzzy grounding scan (extraction_pipeline.py:828 → transcript_utils.py:1750) is O(items × transcript) with no bound and re-runs on the fallback path, burning minutes of CPU precisely on the paraphrased/hallucinated quotes the gate exists to reject. Note the real publish gate still correctly BLOCKS on true unfaithful content, and the judges were calibrated on real artifacts — the core is sound but has these specific holes. Secondary wins: judges re-send the full transcript per artifact with no shared cached prefix and re-run 4x across publish subprocesses (pure cost), and README/config/architecture docs misstate model IDs and the publish-gate layer.

## Top 5 to fix first

1. **Claim-extraction label-strip deletes a fabricated pre-colon specific before the armed faithfulness judge (gate bypass) — faithfulness_judge.py:136** — CONFIRMED high and it defeats the fail-closed core: a hallucinated citation phrased as 'Prefix: ...' is stripped so the Hard-BLOCK judge never judges it; the gold set never tests this class, so calibration reports clean recall while it escapes.
2. **Default 'V2 (Safe)' validator swallows transient/parse failures and returns [] — transcript_initial_validation_v2.py:233,265** — CONFIRMED high, on the DEFAULT path: an unvalidated chunk is indistinguishable from a clean one, so a partial run ships a *_validated artifact masquerading as clean with no failed-chunk signal — P1+P2 fail-open the v1 sibling deliberately raises on.
3. **Stored XSS: untrusted transcript + LLM fields flow unescaped into the HTML/PDF bundle — transcript_utils.py:1642 (+ |safe templates)** — CONFIRMED high security: markdown_to_html does zero escaping and templates render with |safe, so a <script>/onerror payload executes when the shared bundle is opened; no test covers it and the bundle is the distributed deliverable.
4. **Non-dict runtime_settings.json crashes config import app-wide — config.py:64** — CONFIRMED (critical→high): valid-JSON null/[]/int slips past the JSONDecodeError guard and raises AttributeError at module load (config.py:257), so the GUI and every pipeline stage fail to start with no recovery short of hand-fixing the file.
5. **Unbounded O(items × transcript) fuzzy grounding scan on paraphrased quotes — extraction_pipeline.py:828 → transcript_utils.py:1750** — CONFIRMED high scale cliff: the sliding-window SequenceMatcher never early-stops on ungrounded quotes, runs 2–3x per ref plus a full fallback re-run, with no timeout/cap — minutes of silent CPU burn triggered by exactly the hallucinated input the release gate targets.

## Top 3 systemic risks

1. **Fail-open: a transient/error outcome is recorded as an empty-but-benign result (P1/P2)** — The same 'return [] / PASS-on-empty' shape recurs across the fail-closed core: the V2 validator drops a chunk's findings on API failure, its JSON parser returns [] on truncation, check_theme_grounding treats 'no artifacts' as PASS while faithfulness treats it as ERROR, and a non-blocking ERROR ships as ALLOW_WITH_WARNINGS with no distinct log/exit-code/marker signal. In every case 'couldn't verify' is indistinguishable from 'verified clean', so unattended runs silently emit artifacts that look validated. Fix the class by making every consumer distinguish source-absent from parsed-to-nothing and fail closed like the v1 validator.
2. **Duplicated source-of-truth that drifts silently (P4/P19)** — Load-bearing values are copy-pasted instead of referenced, and the copies have already diverged: model IDs are wrong in README (all three) and in the config.py:645 'Defaults' comment; the abstract prompt hardcodes 249/250 vs config.ABSTRACT_HARD_MAX_WORDS; retry/backoff constants and a 900.0 timeout duplicate TIMEOUT_SUMMARY inline; token_usage.csv headers mislabel their columns; runtime deps split between pyproject and requirements.txt; and _fill_prompt_template / load_prompt (×5) / validator-dispatch are byte-duplicated across modules (the last already diverged on the model arg). Any single-site edit leaves the other copies silently stale.
3. **The LLM-judge fail-closed core has real-path and scoping holes (P20/P7)** — The armed judges are trusted as hard blockers but the plumbing around them is under-exercised on the production path: destructive claim extraction removes fabrications before judging (false PASS), the abstract regeneration precheck runs the full multi-artifact faithfulness sweep instead of abstract-only scope (false BLOCK + wasted attempts + misblame), the judge models are floating aliases rather than pinned snapshots, and the gold set never runs the real extraction/scaffolding path so its perfect recall is a mirage. The judge verdict can be wrong in both directions while metrics look clean.

## Strengths to preserve

- The M1 release gate is genuinely fail-closed at the decision level: it refuses to write a bundle on BLOCK, and even when the abstract loop misblames a sibling artifact, the real publish gate still correctly blocks on the true unfaithful content (no wrong-publish results from that bug).
- The v1 initial validator (transcript_initial_validation.py:160-169) deliberately RAISES on both parse failure and exception with an explanatory comment ('fail validation instead of returning empty list') — the correct fail-closed pattern that v2 should have inherited.
- The entity_grounding check is correctly scoped to the abstract only via config-driven suffix lists (GATE_ENTITY_ARTIFACT_SUFFIXES), showing the intended per-artifact scoping is already understood and applied in one place.
- The extraction pipeline already uses create_system_message_with_cache(transcript) as a shared cached system message — the correct prompt-caching pattern exists in-repo and just needs to be applied to the judge calls.
- config.py centralizes timeouts, token caps, temperatures, and thresholds and runs a startup validate_configuration sanity check, giving a single source of truth for most tunables (the drift issues are the exceptions, not the norm).
- Gate verdicts are durably persisted in a machine-readable run manifest, so even the ERROR/couldn't-verify state that is missing from the one-line log is recoverable via the manifest's gate.verdicts array.
- The judges were calibrated on real artifacts with explicit recall/precision bars and the gold set is treated as a living artifact (per project memory), reflecting a P20-aware discipline that should be preserved and extended to the extraction path.

#### [H3] Non-atomic write + silent {} reset loses ALL persisted settings on a partial write

- **Dimension:** concurrency-state  ·  **Status:** CONFIRMED  ·  **verify:CONFIRMED→low**
- **Location:** `config.py:89`
- **Failure scenario:** _save_runtime_settings writes with `path.write_text(json.dumps(...))` (config.py:89) — no temp-file+os.replace, no fsync, no lock. If the process is killed / crashes / hits disk-full mid-write, or two writers interleave, the file is left truncated (e.g. `{"source_dir_favorites": ["/a`). On next launch _load_runtime_settings hits JSONDecodeError, which IS caught (line 65), and silently resets self.runtime_settings to {} (line 66) with no log and no user-facing warning. The user's saved workflow presets vanish with the file appearing to 'reset itself'. Trigger: Ctrl-C / kill the GUI (or a `transcript_process` run) during any set_* call, or a full disk.

- **Evidence:** config.py:85-89 write_text with no tmp/rename/lock; config.py:63-67 JSONDecodeError branch sets runtime_settings={} and returns with no logging.
- **Verifier:** config.py:89 writes runtime_settings via `path.write_text(json.dumps(...))` — an in-place truncate+rewrite with no temp-file+os.replace, no fsync, and no lock, so a kill/crash/disk-full mid-write (or two interleaving writers) leaves a truncated/invalid JSON file. All persisted settings flow through this path: 9 `set_*` methods (lines 134-223) call _save_runtime_settings, covering favorites, default source/processed/projects dirs, stage selections, and validation_approved_terms_path. So a partial write followed by relaunch silently discards every saved preference — a genuine non-atomic-write + P2 silent-drop defect with no guard preventing it. Adjusted down from high because the affected data is recoverable UI-preference state (not documents or pipeline output), the user can re-enter it, and the trigger is a narrow crash window during a single small write or rare concurrent writers.

## Refuted during verification (6)

_Findings a finder filed that an independent verifier could not reproduce — recorded for transparency, not action._

- **The release-gate judges (and all extraction/generation prompts) embed untrusted transcript text with spoofable text delimiters and no prompt-injection guard** (`faithfulness_judge.py:224`, filed medium/SPECULATIVE) — The structural observation (no injection guard, spoofable text delimiters, no "SOURCE is data" clause) is factually accurate, but the concrete failure scenario does not occur. (1) The "pre-supplied all-'entailed' JSON answer inside the transcript" mechanism is a data-flow misread: _parse_judge_response reads verdicts from the MODEL'S response_text, never from the source string, so a JSON blob planted in the transcript is never parsed as the answer. (2) The parser fails closed and strict — every claim must get a valid label by 1-based index or it raises ValueError, which release_gate maps to ERROR (blocking), so garbled/partial steering degrades toward BLOCK, not PASS. (3) The threat model does not fit this app: the transcript is the user's own uploaded content and the same user runs the gate over their own summary — no privilege boundary exists. A user wanting to wave through a fabricated abstract would just set config.FAITHFULNESS_JUDGE_ENABLED=False; injecting into their own transcript to fool their own gate yields nothing an attacker seeks. The only residual is generic prompt-injection defense-in-depth, which is (a) unconfirmable without a live API call (the finding concedes this) and (b) predicated on attacker-controlled transcripts that this single-user pipeline does not present. The cited concrete trigger collapses on inspection.
- **Generation-time faithfulness precheck re-judges ALL narrative artifacts, then the publish gate (separate process) judges them again** (`extraction_pipeline.py:1118`, filed medium/CONFIRMED) — The finding's central mechanism does not hold up against the code. (1) There is NO "separate publish subprocess with an empty memo." Publishing runs through `pipeline.generate_webpage`/`generate_pdf` → `release_gate.publish_allowed` → `check_faithfulness`, all invoked in-process from the GUI (`ts_gui.py` `run_task_in_thread`, background threads of the same process). `release_gate.py` is never invoked as a subprocess anywhere (grep confirms the only subprocess in the flow is pandoc for DOCX rendering in `bundle_export.py`). Because `_FAITHFULNESS_CACHE` is a module-level dict shared across those threads, a sibling artifact's verdict computed at abstract generation is reused at publish — not "re-judged from scratch." (2) The claim that the generation-time precheck "re-judges ALL narrative artifacts (abstract, summary, overview, blog)" is false: the pipeline stage order is structured_summary → gen_abstract → blog → overview → package (`ts_gui.py` `_run_stage_*`). At abstract-generation time only the abstract and summary exist on disk; blog and overview don't exist yet, so `check_faithfulness`'s `path.exists()` skips them (release_gate.py:404). They are judged for the first time at publish, once. (3) Within the regenerate loop, the summary sibling's text is unchanged across attempts, so its sha-keyed memo entry is computed once on attempt 1 and cache-hit on attempts 2–3; only the abstract (legitimately different each attempt) drives new judge calls. The residual kernel of truth — the generation-time precheck judges the summary sibling in addition to the abstract, which the proposed abstract-only scoping would avoid — costs at most one extra judge call for the summary and only if the process is torn down between generation and publish (otherwise the shared memo makes it net-zero). That is a minor smell, far from the described "work paid across the process boundary" for four artifacts. The cited evidence (separate subprocess, empty memo, all four suffixes double-judged) does not survive tracing, so I default to REFUTED.
- **Mutation gate excludes the two fail-closed safety modules it exists to protect (release_gate.py, faithfulness_judge.py)** (`quality_gates.py:78`, filed medium/CONFIRMED) — No wrong behavior occurs.
